# 用 60GHz 毫米波雷达测心率和呼吸：我踩了四个坑

> 一块开发板、一个毫米波雷达模组，不戴手环、不贴电极，人往前面一坐就能看到心率和呼吸。听起来是个标准的雷达信号处理流程，我从"能出数"调到"数是对的"，花了好几个月。这篇文章讲四个坑，以及最后怎么把误差压到 0.3 BPM。

## 先看结果

同一段 60 秒原始位移，板端在线输出和电脑上独立复算的对比：

| 指标 | 板端输出（中位） | 离线复算 | 偏差 |
|---|---|---|---|
| 心率 | 64.3 BPM | 64.0 BPM | +0.3 BPM |
| 呼吸 | 18.4 次/分 | 18.5 次/分 | −0.0 次/分 |

而在修之前，板端心率稳定输出 60，呼吸在 9 到 19 之间反复横跳。

项目叫 AURA，硬件是 RDK X5 + RS6240 毫米波雷达 + CH347 USB 转 SPI，软件分三层：板端 C++ 服务负责采帧和算法，Drogon 提供 REST 接口，Android App 负责展示。代码已经开源，地址在文末。

## 整体链路

```
SPI cube (8 通道 × 30 距离门, 90 Hz)
  └─ 距离维 FFT + 杂波抑制
      └─ 距离门打分 + 滞后锁定
          └─ 多通道复数融合 → 相位
              └─ mm = phase × 5 / 4π
                  ├─ 0.18–0.50 Hz → 30s Welch → 呼吸
                  └─ 1.0–2.5 Hz 因果带通 → 30s 窗
                       ├─ FFT + 谐波积谱
                       ├─ 自相关
                       └─ 峰值间期
                           └─ 三路加权融合 → 1.5 BPM/s 平滑
```

下面四个坑，基本都出在这条链路的后半段。

## 坑一：距离门不是"取最大能量"就完事

第一版代码非常简单：每个窗算 30 个距离门的能量，取最大的那个，拿它的相位。

结果是一堆台阶。

原因是人在呼吸时，胸腔位移有 5–10 mm，这个位移足以让回波能量在相邻距离门之间移动。这一秒最大能量在 17 号门，下一秒跑到 18 号门，两个门的相位基准不一样，差分出来就是一个 1–2 mm 的阶跃。

这些阶跃在时域上看着像小毛刺，在频域上是灾难：一个阶跃的频谱是宽带的，而且能量集中在低频。你的心率带里会凭空多出一堆能量，位置还挺稳定。

解决办法是距离锁定：给每个门打分（能量、相位稳定性、跨通道一致性），只有当候选门连续多帧胜出、且领先优势足够大时才切换，同时对跳门加惩罚。

这一步做完，台阶从每分钟上百次降到几十次，但仍然没有消失。

## 坑二：8 秒窗根本量不出呼吸

第二版把呼吸和心率都放在一个 8 秒窗里做 FFT。

8 秒窗的频率分辨率是多少？1/8 = 0.125 Hz，换算成每分钟是 7.5 次。而呼吸周期本身是 3–5 秒，也就是 12–20 次/分。分辨率和被测对象在同一个量级，这个测量从原理上就不成立。

实际表现是：呼吸输出在 11、14、18、24 之间随机跳，每次跳都"有依据"，因为谱峰确实在那儿。

改成 30 秒窗 + Welch 之后，分辨率提升到 2.6 次/分（nperseg = 2048），输出立刻稳了。

代价是响应变慢：呼吸率的变化要 30 秒才能完全反映出来。对这个场景（静坐监测）可以接受。

## 坑三：呼吸频带的下边界不能拍脑袋

呼吸改 30 秒窗之后，数字是好看了，但我发现它会在 10.5 和 18.5 之间来回跳，两个值差得整整齐齐，正好两倍。

这就是典型的倍频程误判（octave error）。30 秒窗里同时存在两个能量相当的峰：一个是 10.5 次/分的基线漂移，一个是 18.5 次/分的真实呼吸。谁的瞬时能量大一点，输出就跟谁走。

为什么基线漂移会落在呼吸带里？因为我把带通下边界设成了 0.14 Hz，也就是 8.4 次/分。而位移信号的基线漂移本身就是一个缓慢的随机游走，10 次/分附近的能量很大。

把下边界抬到 0.18 Hz（约 11 次/分）之后，漂移被排除，输出稳定在 18.5。

这里有个取舍：抬到下边界之后，10 次/分以下的极慢呼吸就测不到了。静息成人正常呼吸是 12–20 次/分，所以我接受这个代价。如果你的场景包含慢呼吸（比如睡眠监测、呼吸训练），需要另做处理，不能直接抄这个参数。

> 注意：改的是**峰值搜索区间**，不是滤波器。0.18 Hz 以上的信号成分没有被削弱。

## 坑四：你以为的心率峰，其实是呼吸的谐波

这是最坑的一个，也是最值得说的。

心率修完之后，板端稳定输出 60 BPM。我在电脑上用 Python 复算，1.0–2.5 Hz 带内最强峰是 76 BPM。差了 16 BPM，看起来板上钉钉是板端算错了。

于是我开始调板端参数。调了三天，怎么调都是 60 附近。

直到我让受试者报了一下手表读数：**70**。

两个都不对。板端偏低 10，Python 偏高 6。

问题出在哪？

呼吸 18.5 次/分，也就是 0.308 Hz。它的 4 次谐波是 1.23 Hz，也就是 **74 BPM**。5 次谐波是 92.5 BPM。

而心率的搜索带是 1.0–2.5 Hz，正好覆盖 60–150 BPM。

也就是说，呼吸的第 4、5 次谐波稳稳地落在心率带正中间，而且胸廓呼吸位移是毫米级，心搏位移只有 0.05–0.2 mm，谐波的能量比真实心搏大一个数量级。

**"1.0–2.5 Hz 带内最强峰"这个参考值本身就是错的。**

验证方法：把呼吸的 1–8 阶谐波用最小二乘拟合出来，从信号里减掉，再看残差谱。残差主峰落到 60–66 BPM，和真值 70 对上了。

所以正确的顺序是：

1. 先把呼吸估准
2. 再用呼吸频率去挖掉各阶谐波（陷波）
3. 最后才在剩下的信号里找心搏

板端其实一直有陷波器，叫 RHC notch。它的问题不是没做，而是**依赖呼吸频率的准确性**。呼吸估偏 10%，陷波就挖错位置，心率照样被带偏。这也是为什么坑三和坑四是连在一起的。

陷波器还有两个细节：

- 40–60 BPM 的谐波不挖。这一段本身就是低心率区，挖掉的风险大于收益。
- 挖之前先找 3 个最强谱峰和 1 个自相关主峰当"候选"，如果某个谐波在候选 6 BPM 以内，跳过不挖，避免把真实心搏当成谐波削掉。

## 怎么验证：不要相信"看起来平滑"

这几个坑有个共同点：**错误的结果看起来很合理**。60 BPM 是正常心率，10 次/分是正常呼吸，曲线平滑，没有毛刺。如果你只看板端输出，永远发现不了问题。

我的做法是给板端加两个诊断导出开关：

| 环境变量 | 内容 |
|---|---|
| `AURA_PHASE_DUMP` | 逐样本毫米位移 `n,mm` |
| `AURA_SNAP_DUMP` | 逐帧输出 `frame,hr,resp_hz,conf,motion` |

只在设置环境变量时生效，正常运行时零开销。采 60–90 秒，把 CSV 拉回电脑，用 Python 独立复现整条链路。

独立复现的意思是：不用板端的任何中间结果，从 `mm` 开始，用 scipy 重新滤波、重新做 Welch、重新找峰。参数和 C 代码一一对应。然后逐秒对比，差异大的地方就是 bug 所在。

这套流程帮我定位了三个问题：

- **双 pipeline 污染**：回放和硬件雷达同时启动，两路都往同一个 CSV 里写，帧号出现 +100 和 +90 两套序列。修法是硬件雷达启用时强制关掉回放。
- **平滑器启动偏差**：速率平滑器每秒最多变 1.5 BPM，用前几秒的坏值播种后，要一分多钟才能爬回真值。实测启动 60 秒后还停在 68.7。修法是分析窗不足 20 秒时不给平滑器喂数据。
- **心率窗太短**：10 秒窗只有 8–10 个搏动，一次台阶伪迹就能把谱峰拉到 60。改成 30 秒窗，分辨率从 5.9 BPM 提到 2.6 BPM。

## 三路融合的参数

心率最后是 FFT、自相关、峰值间期三路加权：

```
w_fft = clip(snr / 5, 0.1, 1.0)
w_acf = clip(acf_height, 0.1, 1.0)
w_ppi = clip((n_peaks - 4) / 12, 0.05, 1.0)
```

PPI 的权重直接跟搏动数挂钩。10 秒窗里只有 8–10 个搏动，漏一拍间期就翻倍，所以搏动少时必须把 PPI 压下去。

融合规则：

- 三路最大差小于 8 BPM：加权平均
- 不一致，但 FFT 和自相关吻合、PPI 离群：直接丢弃 PPI
- 其他情况：取中位数

## 还没解决的

说几个诚实的限制：

1. **体动敏感**。移动时原始位移里会出现 0.8–1.9 mm 的台阶，心率会短暂失锁。目前只能靠 `motion` 标记提示。
2. **倍频尖峰**。体动时三路可能同时锁到二次谐波，速率平滑器的重锁机制会接受它，出现几帧 130+ 的读数。
3. **只验证了一种场景**。0.6–1.2 米、正面坐姿、单人、静息。多人、侧身、边走边测都没有验证。
4. **不是医疗器械**。所有数字只能当参考，不能用于诊断。

下一步想做的是台阶修复：在相位解缠阶段检测 2π 整数倍跳变并补偿，而不是在频域硬扛。如果做成了，上面的第 1、2 条应该都能缓解。
